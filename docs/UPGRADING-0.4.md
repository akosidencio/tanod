# Upgrading to 0.4

## From 0.4.0 to 0.4.1

0.4.1 changes no configuration, runtime behavior or CLI argument. A 0.4.0
configuration runs unchanged; replace the binary, image or npm packages. What
moved is where the image is published: 0.4.1 and later are at
`ghcr.io/tanod-sh/tanod`, while 0.4.0 and earlier stay at
`ghcr.io/akosidencio/tanod`. Update image references when you change the
version, and pin the digest from the release page. The npm package names
(`@tanod/next`, `@tanod/linux-x64`) are unchanged.

## From 0.3.2 to 0.4.0

**0.4.0 fixes four vulnerabilities that affect 0.3.2 and every earlier
release.** There is no 0.3.3. Upgrading from 0.3.2 straight to 0.4.1 follows
the same steps. Until you can upgrade, apply the mitigations in
the [release notes](RELEASE-NOTES-0.4.0.md#mitigations-for-032-until-you-upgrade);
they reduce exposure but are not equivalent to the fixes.

### In order

1. **Validate the configuration with the 0.4.0 binary** before deploying it:
   `tanod check --config tanod.yaml`. 0.4.0 refuses
   `coalesce.override_origin` on a route without `class:`. Add the class the
   route really has (`class: public_ssr` for a shared page). Policies
   generated by `@tanod/next` 0.4.0 already declare one.
2. **Forwarding headers.** If an edge in front of Tanod rewrites `Host` and
   your origin read the public host from `X-Forwarded-Host`, set
   `server.trusted_proxies.from` to the edge's addresses and
   `server.trusted_proxies.host: x_forwarded`; otherwise Next.js Server
   Actions fail their origin check behind that edge. Test Server Actions and
   absolute redirects in staging.
3. **Raw dot-segment paths.** Find non-browser clients and health checkers
   that send `/./` or `/../` in paths; they now receive `400` in protect mode.
4. **Worker threads.** Tanod now uses every available CPU. If it shares a
   container or host with the app, set `server.threads`.
5. **Origin work and deadlines.** Renders for clients that disconnect now run
   to completion and count against the ceiling. Keep `timeouts.origin` near
   your longest acceptable render, and alert on
   `tanod_origin_disconnect_drains_total{outcome="deadline"}`.
6. **Supervisor deadline.** Set the stop timeout above
   `drain_period + shutdown_timeout` plus a margin (examples: 50 s for 5 s +
   35 s).
7. **Roll out.** Pin the image by digest (`ghcr.io/tanod-sh/tanod@sha256:…`
   from the release page; 0.4.0 itself was published as
   `ghcr.io/akosidencio/tanod`) or verify the archive against `SHA256SUMS`. Roll one
   instance, watch readiness, origin in-flight work, queue depth, cache
   pressure and error rates, then the rest.
8. **Rollback.** Keep the 0.3.2 binary and its configuration together. A
   rollback starts with a cold cache and **re-exposes the vulnerabilities
   fixed in 0.4.0**; reapply the 0.3.2 mitigations if you roll back.

### Every change from 0.3.2

| Change from released 0.3.2 | Automatic behavior | Operator action |
|---|---|---|
| Proxy workers | Omitted `server.threads` uses Rust's available parallelism, respecting visible affinity and quotas, with a minimum of one. | Use `threads: 1` to retain single-worker behavior or leave CPU to a colocated Node process. Values 1–1024 are accepted; zero is rejected. Restart to change it. CPU shares alone are not a CPU quota. |
| Forwarding boundary | Untrusted forwarding fields are overwritten/removed; trusted public host remains off by default. | If the edge rewrites Host, configure its exact source CIDRs and `server.trusted_proxies.host: x_forwarded` (or `forwarded`). Ensure the edge overwrites that header and enforces public hosts. Test Server Actions and absolute redirects. |
| Cache-policy reload | Compatible operational changes retain the namespace. Sharing-policy changes retire and reclaim it before publishing a new generation. Late old writers cannot become eligible for new followers or retain content. | Expect a cold cache after incompatible edits. Purge every replica; caches and coalescing are per process. Existing pinned responses may finish. |
| Cache pressure | Registration pressure falls back uncached; a fill may finish unstored within one maximum body of headroom. Past headroom it aborts visibly. | Budget RSS beyond logical cache bytes, including detached readers, stacks and indexes. Keep large streams off cached routes if the application cannot tolerate the documented first oversized-body abort. |
| In-flight gauges | `/status` and `tanod_origin_in_flight` report actual held weighted units, which can exceed a newly lowered limit until work finishes. `tanod_upgrade_active` counts separate tunnel slots. | Interpret them as work, not request counts. Review saturation alerts after changing weights or limits. |
| Client disconnects | An admitted request whose client leaves, or is cut off at `timeouts.downstream_write`, keeps its permit while Tanod reads the origin's response to its end and discards it, up to the request's `timeouts.origin` deadline. The origin is no longer signalled to stop by a closed connection. Exempt classes and cache fills are unchanged. | Expect renders for departed and cut-off clients to complete and to count against the ceiling. Keep `timeouts.origin` near your longest acceptable render. Alert on `tanod_origin_disconnect_drains_total{outcome="deadline"}`. See [what the origin ceiling guarantees](OPERATIONS.md#what-the-origin-ceiling-guarantees). |
| Operational metrics | `tanod_config_reloads_total{outcome="success"\|"failure"}` and `tanod_process_start_time_seconds` are added. Generation changes only on accepted reloads. | Import updated alert examples; keep scrape-target identity stable for timestamp-based restart alerts, or use orchestrator restart metrics. |
| `coalesce.override_origin` | No longer persists anything: a response it lets past the origin's `no-store`/`private`, and any response to a cookie-bearing request it admits, is shared within one flight only. | Add `class: public_ssr` (or the class the route really has) to every route that sets it; without a class the configuration is refused. If you relied on it to store, which it was documented not to do, use `cache.override_origin` with a `ttl.max`. |
| Query-policy names | `cache.query` keys match the decoded parameter name. A request spelling a listed name with escapes (`%71` for `q`) is now kept by `include` and dropped by `exclude`. | None. Expect at most a few extra or merged entries for such spellings. |
| Dot segments | In protect mode a target whose path has a `.` or `..` segment, literal or `%2e`-encoded, gets `400` and never reaches the origin. Observe mode is unchanged. | None for browsers, which resolve them first. Check non-browser clients and health checkers that send raw `/./` or `/../` paths. |
| Shutdown | SIGTERM withdraws readiness while serving for `drain_period`, then Pingora closes listeners and drains. SIGINT is fast shutdown. | Set the supervisor deadline above drain + shutdown timeout + teardown. The production examples use 50 seconds for 5 + 35 + 1 seconds. Streams/tunnels need reconnect or an appropriate deadline. |

Before rollout, validate configuration with the new binary, record the
image/binary checksum, test on a staging origin, then roll one instance while
watching readiness, origin work, queue depth, pressure and response errors.
Keep the preceding binary and configuration together for rollback. A downgrade
starts a cold cache; in-memory namespaces do not persist across process restarts.

For a fixed separate tier, count surge and terminating pods against the static
capacity partition. The shipped Kubernetes example uses ordered StatefulSet
replacement; a Deployment with zero surge can still overlap terminating pods.
Fence an old process before any forced deletion. For application autoscaling, prefer the existing per-app
process/pod topology in the [deployment guide](DEPLOYMENT-GUIDE.md) rather than
assuming the static separate-tier example coordinates capacity dynamically.
